## 结论与建议

1. **围绕个人实际混淆建立词组。** 词形相似、词义相近和音似是不同问题，应分别讲解和练习。
2. **把自动整理作为核心入口。** 用户提供词列或一句话，系统查找已有组、生成差异内容、支持后续补词和纠正。
3. **训练辨别差异，同时保留基础学习。** 对已认识但易混淆的词直接对照；对完全陌生的词降低同批干扰，先建立基本意义。
4. **复习时间优先使用现有算法。** FSRS 是可复用候选；用户将 A 误选为 B 的关系，需要产品另外记录。
5. **可携带的数据包括学习历史。** 专属词库内容包和完整状态恢复应分别设计。
6. **AI 的结构化输出需要内容校验。** 自动生成可减少整理负担，但不能保证释义、词源和单选答案正确。

## 学习证据及产品影响

| 研究 | 实际发现 | 对本产品的影响 | 不能据此承诺什么 |
| --- | --- | --- | --- |
| Kim & Webb，2022，二语间隔练习元分析：[R01](sources.md#r01) | 纳入 48 项实验、3,411 人、98 个效应量；间隔练习整体有中到大的效果，效果随学习目标和练习条件变化 | 将间隔复习与持续记录列入核心；关注延迟后的表现 | 不能证明某个 App 或某个 FSRS 配置一定优于所有替代方案 |
| Rice & Tokowicz，成人二语词汇实验综述：[R02](sources.md#r02) | 单纯强化母语与外语形式连接的集中重复不足；结合检索练习和语义加工更有价值 | 讲解后安排主动选择、回忆和语境练习 | 不能把所有题型对所有学习者视为等效 |
| Baxter 等，2022，114 名成人：[R03](sources.md#r03) | 实验中对照形似的二语词或伪词有助于学习；效果具有具体条件，语义对照没有相同结果 | 形似辨析可作为首版最明确的特色场景 | 不能把形似研究结论直接推广为“所有同义词一组学更好” |
| Baxter 等，2021，48 名荷兰语儿童：[R04](sources.md#r04) | 对照相似词的收益出现在阅读技能较高的儿童中 | 学习基础不同，需要不同提示和难度 | 不能直接外推到成人中文母语学习者 |
| Nakata & Suzuki，2018 在线 / 2019 卷期，133 名日本大学生：[R05](sources.md#r05) | 语义相关与无关词的后测分数未显著不同，但相关词引发更多干扰错误；间隔对无关词的收益更大 | 单独记录干扰错误；近义词组优先讲清语境，而不是堆积释义 | 不能宣称语义聚类总是有害，也不能认为只加间隔就自动消除干扰 |

由这些证据得到的产品推论：

- 对照展示帮助理解，正式答题需要逐步移除高亮、译文和固定词序等提示。
- 针对常混词要保留错误选择，才能区分“这个词忘了”和“把它认成另外一个词”。
- 同样一道题反复答对，不能直接视为在新语境里也会使用。
- 大组和全新近义词的同时引入，应该根据用户基础和实际错误控制。
- 每日时长、题目难度、题目变化和学习负担都可能影响结果，不能仅展示连续打卡作为成效。

这些是待验证的设计推论，不是上述论文已验证的整套产品机制。

## 记忆算法与学习记录

| 候选方式 | 适合的用途 | 限制 | 当前判断 |
| --- | --- | --- | --- |
| 固定日期表 | 最简单的提醒或早期示意 | 不根据个人记忆反馈调整 | 可用于演示，长期核心不优先 |
| 分盒法 / 简单分级 | 容易理解和实现的自定义复习 | 间隔与个性差异较粗 | 可作为概念参照 |
| SM-2 | 有长期应用经验、实现简洁 | 针对记忆状态的拟合能力与 FSRS 不同 | 若宿主要求可兼容；不同时维护两套主算法 |
| FSRS | 根据记忆反馈和时间安排复习，现成实现可用 | 仍依赖合理的卡片定义、真实评分和数据；不理解词组语义 | 优先候选 |
| 从零训练用户记忆模型 | 未来拥有足够数据时进行研究 | 数据量、标注、评估和维护成本高 | 首版不建议 |

Anki 官方说明中，FSRS 的期望保持率与工作量存在明显取舍；`Hard` 表示困难但回忆成功，忘记应使用 `Again`。因此不能把“答错但差一点”映射到成功等级。[R06](sources.md#r06)

本轮读取的 `ts-fsrs` 已发布元数据为 `6.0.0`，维护方说明该库版本与 FSRS 模型版本独立，当前默认构造器采用 FSRS-7，要求 Node.js `>=24.0.0`，许可为 MIT。[R07](sources.md#r07)、[R08](sources.md#r08)、[R09](sources.md#r09)

Context7 的部分检索结果仍包含较早的 `fsrs()` API；正式选型应以固定版本的发布内容和代码为准。这里记录可用性，不提前锁定本项目的模型版本或运行时。

### 针对易混词的记录设计推论

- 记录正确目标 A 与实际选择 B，方向 `A → B` 和 `B → A` 分开。
- 错误率要带上对应题目的机会数；两个错误来自两次还是二十次练习，含义不同。
- 未在一道题中被测到的其他组员不自动算错，也不因展示过就算已掌握。
- 基础词义记忆、形似辨认和语境选择需要可区分的学习项目，避免把选择题成功直接推导成自由拼写成功。
- 使用提示、看过答案、同组刚出现过的直接线索，应被记录，避免污染无提示表现。
- 新增词组成员仅增加必要项目，不生成所有成员两两组合乘所有题型的庞大题库。
- 先用默认参数，积累真实记录后再考虑个性化拟合；不能用少量样本宣称已准确了解用户记忆曲线。

混淆排序首先作为练习内容选择的依据。任何调整复习时间的规则，都需与所选 FSRS 的状态更新保持一致，不能只篡改到期时间而遗漏实际练习。

## 自然语言添加与持续归组

用户新增需求把 AI 的职责从“生成一段解释”扩展到了“维护一个不断增长的个人词库”。这要求处理已有状态。

推荐采用本地检索加受约束的 AI 判断：

- 精确匹配用于重复检查。
- 字符串距离和字符片段用于找形似候选。
- 具体词义及组目的用于判断近义、构词和个人混淆关系。
- 用户明确的归组与排除指令，作为后续匹配的重要依据。
- 对已有组只引用实际存在的候选 ID；应用端负责验证和保存。

向量相似度擅长发现语义关联，但不等于字形相似，也不能直接判断可替换性。现阶段没有必要仅为“智能”预先引入独立向量数据库。

用户提供 `linear / liner` 时，应形成以实际混淆为依据的组；以后补入 `linen` 等词时，参考既有组与上下文。表面共享 `lin` 的词不能无限自动扩张成一大组。

用户输入的词自动添加与可撤销相结合，可以减少反复确认；存在真实歧义时才选择归属。额外词的用户选择与 API 控制已在第三轮明确，详细规则见 [AI 添加方案](../plan/ai-intake.md)。

## LLM 接口选择

本轮核查接口能力，不进行模型质量排名、价格承诺或真实付费调用。

| 服务方向 | 官方资料说明 | 集成影响 |
| --- | --- | --- |
| OpenAI | Structured Outputs 可约束 JSON Schema，但官方明确说明内容仍可能出错：[R21](sources.md#r21) | 采用结构化词条/词组/题目；另做内容和引用校验 |
| DeepSeek | JSON Output 提供 JSON 格式；文档提示需处理空白内容与截断：[R22](sources.md#r22) | 与严格 schema 能力分开检测；明确失败分类与重试 |
| Ollama | 支持 OpenAI API 子集；本地结构化输出支持 schema，当前云端结构化输出文档有不同限制：[R23](sources.md#r23)、[R24](sources.md#r24) | 可作为本地模型候选；本地与云端能力不能视为完全相同 |
| Claude | 官方提供 OpenAI SDK 兼容层，但更推荐原生 API；兼容参数存在限制：[R25](sources.md#r25) | 若为主要模型，优先评估原生适配 |
| Gemini | 支持 OpenAI 库访问；官方建议新集成考虑原生接口：[R26](sources.md#r26) | 根据用户供应商决定适配层，不假设所有参数通用 |

统一的应用层可定义“生成词组”“给已有组补词”“生成练习”等操作，各供应商适配器负责请求和响应差异。不要把所有供应商差异直接散落在界面组件中。

内容质量比 JSON 合法性更重要：

- 近义词可能在题目给出的语境下都成立。
- 同一个词有多个常见词性和义项。
- 形似关系不证明有共同词根；助记联想不等于真实词源。
- 合成例句不是真实语料引用。
- 模型自报高置信度不等于已验证。

建议先构建一小批人工核对的代表词组，检验释义、题目可判定性和归组准确性，再固定提示与接口支持范围。任何后续评价都应由实际执行数据支撑。

### 成本与响应速度

生成内容与日常复习解耦，复用本地已保存材料。模型请求用于添加、补充、纠正、讲解、新语境或短文生成，以及开放表达反馈；按需或在可控范围内提前准备。重复请求复用任务身份与已有结果，记录 token 用量，限制并发和失控重试。

单次或每月费用需要选定模型、输入规模及调用频率之后才能估计。取消本地任务不保证服务商不计费，界面应区分本地取消与供应商实际完成状态。

## 词汇与例句数据

| 来源方向 | 可以带来的价值 | 需要保留的边界 |
| --- | --- | --- |
| 用户资料和笔记 | 最贴近个人目标和原始上下文 | 保留来源；个人导入不自动取得公开再分发权利 |
| Open English WordNet | 义项、释义和同义词集合可辅助候选检索 | 采用其 CC BY 4.0 条款并保留底层 Princeton WordNet 相关声明；synset 不保证所有语境可互换：[R27](sources.md#r27) |
| Kaikki / Wiktionary | 机器可读的丰富词汇数据，可包含词形、词性等 | 数据保留 Wiktionary 的许可；抽取数据可能有错误，包体也较大：[R28](sources.md#r28)、[R29](sources.md#r29) |
| 商业词典 API | 经过编辑的词义和用法资料 | 授权、缓存、修改、再分发需要按实际协议处理；Cambridge 的评估许可不直接等于产品使用许可：[R30](sources.md#r30)、[R31](sources.md#r31) |
| LLM 生成 | 按个人混淆关系生成对照和练习 | 标记为生成，允许纠正，不伪造权威出处 |

首版可以从用户输入、可编辑的生成内容及经核对的少量示例开始。大规模内置词库、真实语料及发音素材应作为明确的数据接入选择，而非默认把网页词典内容全部打包。

数据来源、来源版本与许可说明应保留到导出中。词条内容、用户学习历史、API 凭证分别管理。

## 导入导出与恢复

本节保留不同格式能力的研究比较。当前项目已明确仅支持[专属格式](../plan/native-format.md)，不再把第三方格式纳入实施候选。

Anki、Mochi 的官方文档均明确区分文本交换与能够保留更完整信息的原生格式。RemNote 的 Anki 导入说明也列出 CSS、JavaScript、某些 TTS 等兼容边界。[R10](sources.md#r10)、[R13](sources.md#r13)、[R15](sources.md#r15)

| 格式 | 优点 | 无法默认保留的内容 | 与当前项目的关系 |
| --- | --- | --- | --- |
| TXT 文件 | 输入成本低 | 显式义项、组关系、历史等 | 不在文件导入导出范围 |
| CSV / TSV | 表格易编辑、交换广泛 | 复杂关系和媒体需要字段约定 | 不在文件导入导出范围 |
| XLSX | 直接利用已有 Excel 资料 | 字段映射、多个工作表、公式值等需定义 | 不在文件导入导出范围 |
| JSON / JSONL | 便于表达嵌套关系和版本 | 需要公开 schema 与迁移策略 | 专属容器的内部编码候选 |
| ZIP 加 JSON 与媒体 | 可以保留完整学习资料 | 需要验证文件完整性、版本和资源引用 | 专属容器的实现候选 |
| Anki `.apkg` | 利用已有卡片与媒体 | 调度、模板及不同模型不能假设完全等价 | 不在文件导入导出范围 |

需要优先解决的实际问题：

- 稳定 ID 与重复导入：同一词、同一义项和同一组不能只靠展示名称粗糙覆盖。
- 导入预览：显示新增、修改、跳过和冲突；保留原始数据以便用户处理异常。
- 历史来源：仅有词表时不推测学习过的次数；别人的分享包不默认带入自己的记忆状态。
- 时间：保留实际作答时间、算法版本与有关时区信息；每日计划按用户时区生成。
- 恢复：在空白资料库中验证词条、组关系、内容及历史是否保持一致。
- 兼容范围：CSV 导出成功不代表导入另一个工具后还能恢复所有关系和进度。

## 平台与架构方向

| 候选 | 有利条件 | 实际取舍 | 资料 |
| --- | --- | --- | --- |
| Tauri 桌面加 SQLite | 本地文件与离线能力直接；复用 Web 界面；支持本地数据库 | Rust / 系统 WebView 工具链、打包升级与端差异需要验证 | [R32](sources.md#r32)、[R33](sources.md#r33) |
| Electron 桌面 | JavaScript / Node 工具链集中，浏览器内核一致 | 发行包包含运行时，应用更新和本地能力隔离需要维护 | [R35](sources.md#r35) |
| Web / PWA | 电脑手机入口统一，便于分发 | 持久存储、备份、凭证请求路径、部署和同步都是实际产品工作 | [R34](sources.md#r34) |
| Anki 扩展 | 复用已存在的学习资料和调度系统 | 需要验证复杂分组交互及跨客户端可用性 | [R06](sources.md#r06)、[R10](sources.md#r10) |

MDN 说明浏览器数据通常以 best-effort 方式存储，可以请求 persistent storage；用户仍能主动清除数据。因此使用浏览器并不妨碍离线，但必须明确持久化与备份策略。

Tauri 的多平台支持不自动意味着同一个界面在手机上已好用，也不提供本产品的同步冲突规则。若手机是常用入口，需要从开始就设计相应交互和数据流。

无论选哪种平台，都建议共享一套词条、义项、组关系和作答记录模型。避免界面本地状态、AI 聊天记录和数据库分别维护三套互相冲突的事实。
